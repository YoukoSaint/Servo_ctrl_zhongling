# 众灵舵机真实通讯笔记

> **测试日期**: 2026-07-03
> **串口**: COM8 @ 115200 8N1
> **固件**: ZL-ZServo_AD_CBM V2.1.16
> **协议文件**: `protocol.md`（基线）→ `src/protocol.py`（实现）

## 1. 与手册的差异

手册描述的是旧版固件（v0.97）。实测固件 v2.1.16 有三类主要差异：

### 1.1 版本应答格式不同

| 来源 | 格式 |
|------|------|
| 手册（v0.97） | `#000PV0.97!` |
| 实测（v2.1.16） | `#000@ ZL-ZServo_AD_CBM V2.1.16STG!` |

特征：`@` 替代了 `PV` 前缀，后面跟着 `<型号> V<版本号>`。`STG` 后缀可能是固件分支标识。

**parse_response 已适配**（`protocol.py` line 335-337）：在 `PV` 匹配之前优先匹配 `@` 前缀。

### 1.2 写指令静默执行

v2.1.16 固件中，以下指令**不返回任何应答**：

- `#000P1500T1000!` (move) —— 静默
- `#000PULK!` (release) —— 静默
- `#000PULR!` (recover) —— 静默
- `#000PDPT!` (pause) —— 静默
- `#000PDCT!` (resume) —— 静默
- `#000PDST!` (stop) —— 静默

**影响**：
- 上位机**不能期望**写指令返回 `#OK!`。所有超时判断都是误判。
- 唯一确认写指令生效的方法是：发写指令后再发一条读位置，看 PWM 是否变化。
- 已修复 `scripts/serial_smoke.py` —— 写指令用 `_ok_sent()`（只看 TX 计数），不用 `_ok()`。

### 1.3 PMOD 读不支持

`#000PMOD!` 在此固件上完全无应答。可能是 v2.x 不再支持读取模式，或者该功能合并到其他指令中。

`action_probe()` 已改为用 PID 替代 PMOD。

## 4. 未测指令（推测行为）

以下指令未用真实舵机测试（担心破坏已有配置）：

- `#000PMOD1!` ~ `#000PMOD8!` —— 设置工作模式
- `#000PSCK!` —— 校准中位
- `#000PCSD1500!` —— 设置自定义中位
- `#000PSMI!` / `#000PSMX!` —— 设最小/最大值
- `#000PCLEO!` —— 部分复位
- 群控 `{G ... }` —— 多舵机同步

请在实际使用这些功能前，先通过 `scripts/serial_smoke.py` 的 REPL 逐条验证后再上 UI。

## 5. 排查遗留的 `#OK!` 超时问题

如果你在 UI 上看到"无应答"的提示，但舵机实际动了，原因就是 v2.x 固件写指令静默。排查方法：

```
1. 看 logs/*_protocol.log — 如果有 TX 行但没有 RX 行 → 静默，正常
2. 看 logs/*_health.log — 如果 since_last_rx_frame 很大但 since_last_tx 很小 → 正常，新发送了但没有收到回执
3. 用 serial_smoke.py 直接发 move 然后读位置验证
```

**注意**：`ServoClient` 的 `_write()` 返回 True 仅靠发送成功，不依赖应答。所以 UI 和 controller 层的"无应答"提示应该是 **UI 前端添加的**，不要误读为协议层故障。
